## #1 [high] 自审守卫 team bypass
- **位置**：`riveredge-backend/src/apps/kuaizhizao/services/reporting_service.py:1971`（approve_reporting_record 内）
- **不变量**：审核分离 — 报工人不得自审通过自己的报工记录；小组报工（`team_id` 非空、`worker_id=None`）同样应拒绝小组成员自审。
- **复现步骤**：
  1. 启用报工审核（audit_required=True）。
  2. 以小组模式报工：`team_id=7`，`worker_id=None`，状态落 pending。
  3. 同一组成员（user 42）调用 approve。
- **期望**：小组报工应校验 `recorded_by` / `team_id` 归属，组成员不可自审。
- **实际**：守卫只比较 `int(approved_by) == int(getattr(record, "worker_id", 0) or 0)`，worker_id 为 None → 0 → 42 != 0 → 放行。任何用户（包括提交小组的成员）可自审通过小组报工。
- **严重级**：high（审计分离失效，可虚增合格产量 / 绕过质检门禁）
- **关键词**：`worker_id` `team_id` `approve_reporting_record` `审核分离` `自审`

## #2 [medium] 驳回不回滚计数
- **位置**：`reporting_service.py:1966-1975`（approve 路径 set `rejected`），计数累积在 `reporting_service.py:1320-1328`（create 路径）
- **不变量**：工序的 completed/qualified/unqualified 计数只统计有效报工；rejected 不应永久污染工序累计。
- **复现步骤**：
  1. 报工 50（合格 40 / 不合格 10），create 时 op.completed += 50、qualified += 40、unqualified += 10。
  2. 审核驳回（rejection_reason 非空）。
- **期望**：驳回后应回滚或标记该笔不计入累计，或至少不阻止后续正确重报。
- **实际**：`record.status = 'rejected'` 直接落库，**没有**减回 op 计数。工序累计被 40 合格 + 10 不合格永久虚增；后续重报同数量会再次累计，使 op 累计远超计划。
- **严重级**：medium（数据一致性：工序/工单累计虚高，完工判定、可报余量、质检放行口径受影响）
- **关键词**：`rejected` `completed_quantity` `unqualified_quantity` `回滚`

## #3 [medium] create_reporting_record 无顶层事务
- **位置**：`reporting_service.py:924`（`create_reporting_record` 全程无 `in_transaction`；`in_transaction` 仅出现在 approve(1928)/revoke(2081)/batch_revoke(2217)/delete(2299)/scrap(2726)/defect(2849)/correct(2971) 路径）
- **不变量**：一次报工写记录 + 更新 op 计数 + 更新工单状态 + 触发倒冲/入库应原子；中间失败不应留下半状态。
- **复现步骤**：
  1. 末道工序报工，自动审核通过。
  2. 报工记录已落库 + op 计数已累加 + wo.status 已置 in_progress 后，`_maybe_trigger_direct_finished_goods_inbound`（1492）或审批流收尾（1506 approve）中途抛错。
- **期望**：事务回滚，报工记录与计数、工单状态一致。
- **实际**：无顶层事务，前面已 autocommit 的写留半状态；后续失败只让 API 报错，但 DB 里记录/计数已生效。
- **严重级**：medium（事务边界缺失，库存/计数与单据可能不一致）
- **关键词**：`in_transaction` `create_reporting_record` `原子性` `半状态`

## #4 [medium] 返工余量检查 TOCTOU（读侧带写）
- **位置**：`rework_order_service.py:1585`（remaining 余量检查），依赖 `rework_order_workflow.py:76-92` 的 `sync_link_quantities_from_reports` → `link.save()`（在 `create_rework_reporting` 的 `in_transaction`(1614) 之前的读侧步骤 1577）
- **不变量**：返工合格数量不得超过 `link.input_quantity − link.qualified_quantity`（剩余可返工投入量）。
- **复现步骤**：
  1. 同一 rework_order 当前 link，两个并发 create_rework_reporting。
  2. 两者都先 `sync_link_quantities`（读侧落库到 link 行），再各自算 remaining 并校验。
- **期望**：余量校验应在事务 + 行锁内完成，并发时后者读到前者提交后的已用量。
- **实际**：`remaining` 基于读侧快照计算；无行锁/`select_for_update`，并发两笔可能都通过余量检查，合计超出投入量。另：`execute` 能力层（document_action_policy/rework_order.py:92）仅按 status∈{released,in_progress} 且 `not awaiting_route_decision` 判定，**不**校验 current_link 是否激活 —— 执行层靠 `ctx["current_link"]` 兜底拦截，能力层与执行层语义不一致。
- **严重级**：medium（并发下可超投入量返工，影响库存与工序口径）
- **关键词**：`TOCTOU` `select_for_update` `input_quantity` `sync_link_quantities_from_reports` `execute capability`
