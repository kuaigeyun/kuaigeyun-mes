# Page Normalizer（页面规范化治理）

## 目标

- 在不影响功能的前提下，逐步统一项目规范与代码风格，降低长期维护成本
- 把“规范”变成可执行、可量化、可验收的流程，而不是一次性重构
- 每次改动都可回滚、可验证、可持续推进

## 强制工作方式（必须遵守）

### 任何代码修改前，必须先给出“执行方案”，并等待用户确认

- 在执行任何文件变更前，先输出本次准备做什么，包含：
  - 目标页面/模块与范围边界
  - 具体改动清单（会动哪些文件、改哪些点）
  - 风险点与规避策略（如何保证不破坏功能）
  - 验证方式（类型检查/lint/关键 e2e/手动检查路径）
- 明确提示“等待确认后再动手”
- 只有用户确认后，才能开始编辑文件/提交变更

## 适用触发（何时调用）

- 用户提出：规范化、统一风格、代码优雅化、治理技术债
- 用户提出：I18N 补齐、硬编码清理、过期代码清理、兜底策略清理
- 用户提出：竞态/多逻辑竞争问题、重复提交、请求乱序回写
- 用户提出：性能瓶颈提升（大列表、频繁重渲染、过多请求、首屏慢）
- 在对“系统级/平台级关键页面”准备做较大改动前，用于先制定可执行计划与验收清单

## 核心原则

- 先立门禁再修旧账：让新增代码先合规，再逐步治理历史代码
- 小步快跑可回滚：机械改动与逻辑改动拆分，减少风险
- 用户可见优先：文案、交互、错误提示、空态/loading、性能与竞态优先于“纯洁癖重构”
- 单一来源：枚举/权限/路由/表单 schema 等避免散落硬编码
- 可验证：每次改动都必须能被检查（lint/tsc/e2e/关键路径自测）

## 页面规范化治理流程（建议按阶段推进）

### Phase 0：基线盘点（输出清单 + 指标）

- 盘点：路由 → 页面组件 → 关键子组件 → 依赖服务/接口
- 记录每页指标（建议 0/1/2 评级）：
  - I18N 覆盖率（用户可见文案是否全部来自 t()）
  - 硬编码密度（魔法常量、状态映射、权限码、路径）
  - 兜底策略（吞错、静默 fallback、重复兜底）
  - 竞态风险（并发请求、重复提交、状态回写）
  - 性能风险（大列表、频繁重渲染、无分页/虚拟化、重复请求）
  - 过期代码（未引用、废弃分支、陈旧 feature flag）

### Phase 1：统一写法与门禁（把规范变成自动化）

- 格式化与静态检查：Prettier / ESLint / TypeScript 严格度逐步提升
- 质量门禁：PR/CI 必跑（类型检查 + lint + e2e smoke/关键路径）
- 改动拆分：机械格式化与逻辑调整分开提交

### Phase 2：注释规范化（清噪音，保留 Why）

- 只写 Why/约束/边界条件，避免注释重复代码含义
- TODO/FIXME 统一格式（原因/条件/链接），避免永久遗留
- 优先删除无价值注释，其次为复杂逻辑补充 Why（仅在确需时）

### Phase 3：I18N 补齐（建立 Key 规范 + 防漏机制）

- Key 命名建议：
  - 页面：pages.<scope>.<page>.<section>.<token>
  - 组件：components.<component>.<token>
  - 通用：common.<token> / actions.<token> / errors.<token>
- 硬规则：
  - 用户可见文字（标题/按钮/提示/空态/校验/错误）必须走 t()
  - 枚举/状态映射必须可国际化（避免页面内写中文映射）
- 防漏机制：
  - 扫描 UI 目录中文硬编码（可允许注释/测试例外）
  - 校验多语言 key 一致性（避免只加中文不加英文）

### Phase 4：硬编码清理（常量、枚举、权限、路由、schema）

- 枚举/状态：集中到模块常量或统一 constants/enums
- 权限：集中定义并类型化，避免散落字符串
- 路由：path 常量化；标题/菜单走 i18n
- 表单：schema 与校验消息仅存 key，不存中文

### Phase 5：过期代码清理（可证明没用才删）

- 静态引用分析：未引用导出/死文件/死路由/死分支
- 动态引用审慎处理：插件/配置驱动路径先确认再删
- 删除后必须跑关键验证（类型检查 + e2e smoke/关键场景）

### Phase 6：兜底策略清理（错误处理一致化）

- 请求层：错误归一（鉴权/网络/业务码），页面只决策展示
- UI 层：Empty/ErrorState/Loading 组件化，避免每页自造
- 兜底分级：
  - 可恢复：提示 + 重试
  - 不可恢复：错误页/上报 + 引导
  - 静默兜底必须可追踪（至少可定位，不允许悄悄吞掉）

### Phase 7：竞态治理（并发请求、重复提交、状态回写）

- 请求竞态：路由/筛选切换时避免旧请求覆盖新状态（Abort/序列号/最后一次生效）
- 重复提交：统一 submitting 状态 + 禁用按钮 + 幂等策略
- 状态源统一：URL 参数 / store / local state 明确单一真相来源与同步规则

### Phase 8：性能提升（先量化再优化）

- 列表：分页/虚拟化、columns/render memo、减少不必要的 store 订阅
- 请求：去重、缓存、预取（路由 prefetch 等）
- 渲染：拆分重组件、减少派生计算与重渲染
- 打包：路由拆包、延迟加载低频模块、排查超大依赖

## 页面级验收清单（每次改一个页面就按此验收）

- I18N：无用户可见硬编码；新增 key 多语言齐全
- 状态：loading/empty/error 展示统一且文案一致；无吞错
- 竞态：切换筛选/路由无旧数据回写；无重复提交
- 硬编码：枚举/权限/路径/label 来源统一
- 类型：无新增 any（或明确隔离层）；接口模型一致
- 性能：交互无明显卡顿；无明显多余请求
- 清理：无新增 dead code；无残留调试输出

## 输出模板（执行方案）

在任何变更前，按以下结构输出并等待确认：

1. 范围：本次涉及的页面/模块与不做的内容
2. 改动清单：会动的文件列表与每个文件的改动点
3. 风险与回滚：潜在风险、如何降低、如何回滚
4. 验证方式：会执行哪些检查（lint/tsc/e2e/手动路径）
5. 等待确认：明确提示“确认后开始修改”
