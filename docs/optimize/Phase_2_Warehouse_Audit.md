# Phase 2: 仓储管理审计报告 (Role-Driven 3-Step Audit)

**审计结论**：仓储模块目前处于“录入式”管理，缺乏 ERP 核心的“控制性”逻辑。存在严重的超量收发、价格篡改、质量规避以及库存并发冲突风险。

---

## 第一步：角色视角补齐 (Step 1: Roles & Scenarios)
本阶段审计从以下视角穿透：
- **库管员 (Warehouse Clerk)**: 关注实物入库、资产保全、批次隔离、发货时效。
- **盘点员 (Inventory Auditor)**: 关注盘点快照准确度、实物差异穿透。
- **财务成本岗 (Cost Accounting)**: 关注入库资产估值、移动平均价受贿点。

---

## 第二步：字段缺失与基础业务点审计 (Step 2: Fields & Basic Points)

### 2.2 成品入库批次号录入字段缺失 (Missing Batch Field)
- **问题描述**：成品入库表单中缺失批次号（Batch ID）的录入或系统自动生成器挂载。
- **技术证据**：见 `inbound/index.tsx` 第 378 行：`batchReceipt` 接口载荷中未包含批次属性传递设计。
- **业务影响**：导致成品入库后全为“空批次”，生产工人领料时无法根据批次指令作业，制造溯源链全线熔断。

### 2.3 质检流程规避漏洞 (Validation Gap)
- **问题描述**：库管员在入库表单中可直接输入“合规数量”与“不合规数量”，无需经过品管（QA/QC）角色判定。
- **技术证据**：见 `inbound/index.tsx` 第 730-731 行：系统允许在入库瞬间自申质量状态，完全绕过了 `quality-execution.ts` 的强制联动。
- **业务影响**：质量关口名存实亡，不合格品可在无 QA 知情的情况下强行变更为“合格”上架。

### 2.4 租户 ID (Tenant ID) 泄露风险 (Field Privacy Gap)
- **问题描述**：`tenant_id` 直接暴露在前端接口定义及 Payload 模型中。
- **技术证据**：见 `inbound/index.tsx` 第 34, 65 行：接口 Interface 将租户 ID 显式列出。
- **业务影响**：恶意用户可能尝试通过修改 Payload 中的租户 ID 探测其他企业的私有库存数据（数据越权扫描）。

### 2.5 批次/序列号出库校验缺失 (Verification Gap)
- **问题描述**：出库时的批号录入仅为文本框采集，未与库存现有批次进行存量匹配校验。
- **技术证据**：见 `outbound/index.tsx` 第 607-618 行：仅使用 `ProFormText` 记录批次特征，`handleFormFinish` 中无合法批次前置验证。
- **业务影响**：库管员可录入库房中根本不存在的批号完成发货，导致账务批次与实物批次彻底脱轨。

## 第三步：重大逻辑谬误审计 (Step 3: Major Logical Fallacies)

### 2.1 采购入库超量拦截缺失 (Core Enforcement Broken)
- **问题描述**：入库动作未对源 PO 的剩余待收量进行硬校验，允许超量强制收货。
- **技术证据**：见 `inbound/index.tsx:L728`：`receipt_quantity: Number(it.receipt_quantity) || 0` 直接取值，缺乏后端基于事务锁的阈值对比。
- **业务影响**：库管员可随意扩大入库数，造成实物资产虚高且产生巨额无法核销的财务冗余。

### 2.6 入库端采购价篡改风险 (Role Authority Broken)
- **问题描述**：库管员在收货时可以手动修改“单价”，这本应是采购岗的独占权限。
- **技术证据**：见 `inbound/index.tsx:L729`：`unit_price: Number(it.unit_price) || 0` 显式允许作为编辑入口参与提交。
- **业务影响**：**极高财务风险**。采购成本在入库节点可被任意抹平或虚增，直接摧毁移动平均价核算体系，导致利润表严重失真。

### 2.7 盘点账面快照篡改风险 (Audit Integrity Broken)
- **问题描述**：盘点录入时允许库管员手动填写“账面数量”，而非系统自动锁定的快照数。
- **技术证据**：见 `stocktaking/index.tsx:L570-577`：`book_quantity` 使用可编辑控件，允许传入自定义数值覆盖系统快照。
- **业务影响**：库管员可通过串改账面数来粉饰实物亏损，使盘点审计失去应有的监管意义。

### 2.8 批量出库关联数据丢失 (Data Integrity Broken)
- **问题描述**：从销售订单批量下推发货时，代码未传递具体的待发数量字典，强制执行总量下移。
- **技术证据**：见 `outbound/index.tsx:L164-168`：`pullFromSalesOrder` 仅传递了主单 ID，缺失行级数量分布参数。
- **业务影响**：导致分批次发货逻辑失效，系统无法准确记录部分发货状态，造成订单交付跟踪全线瘫痪。

### 2.9 库存预占与锁定机制真空 (Inventory Logic Broken)
- **问题描述**：系统缺乏 ATP（可承诺量）逻辑。不同单据可以同时指向同一物料余额，无前置锁定。
- **技术证据**：全文搜索 `lock` / `reserve` 无任何针对库存行（Inventory Row）的锁定标志位。
- **业务影响**：在大负荷作业下，会出现“一货多发”的并发逻辑冲突，库管员基于虚高的“实有库”签领。

### 2.10 库存调拨在途资产监控缺失 (Asset Visibility Gap)
- **问题描述**：调拨操作采用瞬间转移逻辑，忽略了跨地域、跨仓库的实物位移过程。
- **技术证据**：见 `inventory-transfer/index.tsx:L167`：直接调用 `execute` 完成余额迁移，无“发货-在途-妥收”的三段式管控逻辑。
- **业务影响**：资产在中转期间处于不可控状态，一旦发生中途失货，系统无法锁定责任仓。

### 2.11 合格/不合格判定量非守恒谬误 (Calculation Parity Broken)
- **问题描述**：手动修正数量的优先级逻辑可导致明细数值之和与单据总数背离。
- **技术证据**：见 `inbound/index.tsx:458`：修正逻辑 `qualified + unqualified > qty ? qty : qualified`。
- **业务影响**：产生账务偏差。高层汇总报表与底层收货明细在金额和数量上无法完美对平。

### 2.12 允许负向合格数量入库 (Validation Bypass)
- **问题描述**：明细子项未对数值录入进行非负截断拦截。
- **技术证据**：见 `inbound/index.tsx:730-731`：代码中使用 `?? 0` 进行兜底，但未检查输入值是否 `< 0`。
- **业务影响**：允许通过负数录入实现“虚假冲库存”，破坏库存余额扣减逻辑。

### 2.13 “在制品 (WIP) 虚假入库”逻辑 (Audit Gap)
- **问题描述**：缺乏针对“工序间拨付”或“半成品”的专用入库逻辑，所有非采购入库均被粗暴归类为“成品入库”。
- **技术证据**：见 `inbound/index.tsx` 第 37 行：`receipt_type` 仅定义了三类。
- **业务影响**：**在制品资产黑洞**。当 A 车间完工转 B 车间暂存时，由于没有专门的“工序拨付入库”，这部分价值数百万的 WIP 在系统账面上处于“自由漂浮”状态，无法实现车间级成本核算。

### 2.14 批次号 (Batch) “魔术化”生成谬误 (Logical Fallacy)
- **问题描述**：入库单上的批次号为选填字符串，而非由系统根据“工单+日期”或“采购+日期”强制生成的 Trace-ID。
- **技术证据**：见 `inbound/index.tsx` 第 78 行：字段类型为可空的 `string`，且创建接口无自动编号逻辑。
- **业务影响**：**追溯链断裂**。手工输入的批次号极易出现录入错误（如 O/0 混淆），导致一旦发生质量投诉，无法在数秒内精准定位到原材料供应批次或生产班组。

### 2.15 采购退货 (Return) 与财务借项单脱节 (Integration Gap)
- **问题描述**：退货给供应商的操作在仓储端仅为“负向调整”，未自动触发财务端的“进项税额转出”或“供应商扣减”。
- **技术证据**：见 `inbound/index.tsx` 第 36、501 行：退料逻辑仅涵盖生产，缺失 PO Return 的原子化联动。
- **业务影响**：**资金流失风险**。仓库已退货，但财务由于缺乏自动通知，仍按原采购单 100% 结算，导致企业多付货款。

---
> [!IMPORTANT]
> **审计建议**：必须强行封锁入库单价编辑权限，引入 `BigDecimal` 处理金额，并对收货通知单下推实施事务级余量强指。

### 4.1 业务蓝图逻辑检查 (Blueprint Integrity)
- **发现**：`BusinessFlowConfig.tsx:142` 逻辑图中，`assembly_order` 与 `inventory_transfer` 等高级节点在 `small` 模版中默认关闭。
- **实情谬误**：中小制造业常有“边生产边组装”的情况，`assembly_order` 的关闭导致用户被迫使用“其他出入库”代替，造成库存逻辑混乱。
- **证据**：`f:\dev\riveredge\riveredge-frontend\src\pages\system\business-config\BusinessFlowConfig.tsx:142`

### 4.2 参数设置有效性对账 (Parameter Effectiveness)
- **发现**：`warehouse.batch_management` 虽然在配置页呈现，但系统全局并未实行“强制批次追溯”，导致 SME 开启后亦无实际阻断。
- **配置建议**：增加 `warehouse.negative_inventory_allow_limit` 参数。SME 经常需要“负库存”运行（先发货后录入），目前系统缺乏“允许负库存范围”的弹性逻辑，仅有硬性阻断或放任。

### 4.3 静态库龄 (Inventory Aging) 分析真空 (Aging Analysis Gap)
- **发现**：系统仅记录当前库存数量，缺乏基于入库时间轴的“库龄分析”报表与预警。
- **技术证据**：见 `warehouse-management/inventory/index.tsx`：搜索 `age` 或 `aging` 结果为 0。
- **业务影响**：**呆滞料积设风险**。中小型企业往往没有精细的 FIFO 强制执行，缺乏库龄报警会导致大量原材料过期或贬值而无人知晓，造成隐形成本流失。

### 4.4 盘点损益 (Stocktaking) 调账逻辑断层 (Adjustment Gap)
- **发现**：盘点实测值与系统账面值产生差异时，系统不具备“一键生成损益单并核销”的自动化逻辑。
- **技术证据**：见 `stocktaking/index.tsx`：盘点完成后仅停留在“差异报告”，缺乏自动化 Inventory Adjustment 接口的事务性调用。
- **业务影响**：盘点流于形式，由于调账繁琐（需手动录入其他出入库），导致系统账面长期与实面不符，失去管理效能。

## 五、 改进与整改计划 (Step 5: Improvement Plan)

### 5.1 短期整改 (Immediate Actions - 1个月内)
- **[针对 2.6, 2.7]**: **权限漏洞封锁**。立即在 `inbound/index.tsx` 中将 `unit_price` 设为 `disabled`，严禁库管修改采购单价；在 `stocktaking/index.tsx` 中将 `book_quantity` 设为只读，锁定系统快照。
- **[针对 2.3, 6.2]**: **质量门槛同步**。修改入库逻辑，当物料属于“必检”类别时，取消手动输入合格数的权限，强制关联已审核的 `inspection_report_id`。
- **[针对 2.4, 10.7]**: **多租户隔离加固**。从前端界面彻底移除 `tenant_id` 显式字段，改由后端从 JWT 令牌中自动提取，杜绝数据探测风险。
- **[针对 2.12, 7.6]**: **数值非负验证**。在全局入库/出库 `handleSave` 逻辑中增加 `quantity > 0` 验证逻辑，封锁通过负数绕过业务校验的漏洞。

### 5.2 中期优化 (Medium-term - 3个月内)
- **[针对 2.1, 7.11]**: **采购合规校验 (3-Way Match)**。在入库保存时，后端必须实时查询 PO 剩余待收量，并在数据库事务级执行 `Check(inbound_qty <= PO_remaining_qty)`，防止超量虚假收货。
- **[针对 4.3]**: **决策支持增强**。开发“动态库龄分析引擎”，基于入库批次时间戳自动计算呆滞时长，并在看板中对超过 90 天未移动的物料执行“降值预警”。
- **[针对 4.4]**: **盘点闭环自动化**。实现盘点差异确认后的“自动调账”功能，一键生成“其他出/入库单”并自动核对损益科目，确保存货实时账实相符。

### 5.3 长期演进 (Long-term Strategy)
- **[针对 2.14, 2.9]**: **批次/序列号自动治理**。实现全局批次号 (LPN) 自动生成算法，打通从生产/采购到入库的唯一 Trace-ID 链路，并引入 Redis 行级锁保护高频出入库场景下的数据原子性。
- **[针对 2.13]**: **车间资产透明化 (WIP Tracking)**。建立专门的“在制品拨付”事务类型，实现 A 车间产出 -> 线边暂存 -> B 车间领用的全流程价值追踪。
