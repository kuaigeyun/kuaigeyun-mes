# Phase 5: 工程与 BOM 逻辑审计报告 (Role-Driven 3-Step Audit)

**审计结论**：主数据逻辑目前仅能支撑“静态展示”，无法支撑“动态控制”。BOM 与工艺路线的脱节、ECN 变更的闭环缺失，导致生产线边仓混乱与版本错误（旧版件装入新产品）风险。

---

## 第一步：角色视角补齐 (Step 1: Roles & Scenarios)
本阶段审计从以下视角穿透：
- **工艺工程师 (PE)**: 关注 BOM 准确性、M-BOM 挂载、工艺路径。
- **变更管理者 (ECN Coordinator)**: 关注工程变更版本切换、在制品处置。

---

## 第二步：字段缺失与基础业务点审计 (Step 2: Fields & Basic Points)

### 5.2 M-BOM 逻辑断层（无工序消耗关联） (Missing Field/Link)
- **问题描述**：BOM 组件无法指定到具体的工艺路线工序（Operation ID）中。
- **技术证据**：见 `routes/index.tsx` 第 572-649 行：工艺路线仅展示工序序列，无物料挂接槽位（Empty Linkage）。
- **业务影响**：MRP 只能计算出“工单开工日”需要所有物料，而无法按照工序进度“拉动式”供料。结果：生产开工即伴随大量线边堆料，增加管理成本。

### 5.3 ECN（工程变更）发布的“断尾”逻辑 (Flow Gap)
- **问题描述**：新版 BOM 发布后，系统未提供“对现有工单的影响分析”，导致在制品处理无逻辑闭环。
- **技术证据**：见 `bom/designer.tsx` 第 149 行：仅处理界面只读权限，不触发生产下游的版本同步动作。
- **业务影响**：旧版本 BOM 的工单仍按旧图纸加工，版本切换出现时间断层，导致“带病交付”或产生过期呆滞料。

### 5.4 损耗率 (Waste Rate) 参数失效化 (Field Gap)
- **问题描述**：BOM 中虽有损耗率设置，但在采购申请（PR）与生产工单（WO）计算中未应用。
- **技术证据**：见 `bom/designer.tsx` 第 300 行：该字段仅作为数据存储，未参与 MRP 乘积运算公式。
- **业务影响**：系统在实际计划生成中忽略了工艺损耗，导致账面总是“理论缺料”，实际采购/领料量恒定偏少。

## 第三步：重大逻辑谬误审计 (Step 3: Major Logical Fallacies)

### 5.1 BOM 循环引用缺乏全局校验 (Recursive Logic Broken)
- **问题描述**：系统仅在前端 MindMap 编辑时有局部检查，缺乏全局递归校验（A->B, B->A）。
- **技术证据**：见 `bom/utils.ts` 第 101-102 行：`findNode` 仅为当前会话树校验，未针对数据库存量进行深层扫描。
- **业务影响**：**服务器崩溃风险**。MRP 计算时将陷入无限循环，消耗全部 CPU 资源并导致系统全局僵死。

### 5.5 替代料 (Substitute Material) 映射逻辑真空 (Reference Logic Broken)
- **问题描述**：BOM 明细行缺乏“主/替”物料的逻辑权重与自动切换配置。
- **技术证据**：见 `bom/designer.tsx` (全文件)：无替代物料（Sub-List）表结构及下推逻辑支撑。
- **业务影响**：缺料时 PMC 无法通过系统直接执行替代方案，必须手动修改 BOM，导致设计严肃性受损且历史记录混乱。

### 5.6 跨租户 BOM 模板共用导致的越权风险 (Security Broken)
- **问题描述**：BOM 保存接口对 `material_id` 的归属校验不严。
- **技术证据**：见 `bom/services.ts:L31`：保存时未强制验证 `material_id` 是否属于当前 Session 的 `tenant_id`。
- **业务影响**：恶意用户可能修改 ID，尝试探测或改写其他企业的核心技术 BOM 方案。

### 5.7 BOM 版本变更的“影响孤岛”谬误 (Integration Gap)
- **问题描述**：工程变更（ECN）发布新版本后，系统不提供“存量工单替换分析”工具，导致已下达的工单仍按“旧设计”生产。
- **技术证据**：见 `bom/designer.tsx` 第 149 行：`isReadOnly` 仅用于界面锁定，不具备后端同步推送到 `WorkOrder` 状态看板并触发“变更申请”的功能。
- **业务影响**：**重大呆滞料风险**。设计已改版（如更换更便宜的物料），但生产线由于信息断层，继续消耗昂贵的旧料生产已淘汰的产品，造成企业数以万计的资金损耗。

### 5.8 替代料 (Substitute) 的“盲目性”优先级谬误 (Logical Fallacy)
- **问题描述**：替代料优先级仅为静态排序，不具备“基于实时库存自动推荐”的算法驱动。
- **技术证据**：见 `bom/designer.tsx` 第 308、767 行：优先级仅为手动调整的 `priority` 字段。
- **业务影响**：**计划执行效率低下**。当主料缺货时，计划员必须手动去一个个翻替代料库存并手动修改工单，无法实现系统级的“全自动智能替代”。

### 5.9 BOM 递归校验的“前端软防御”风险 (Security Broken)
- **问题描述**：循环引用（A->B->A）的死循环校验仅存在于前端 Designer 逻辑中，后端 API 缺乏物理硬约束。
- **技术证据**：见 `bom/utils.ts` 中的 `findNode` (Client Side)。保存接口 `bomApi.save` 缺乏深层递归死循环的前置检查。
- **业务影响**：**系统全局崩溃风险**。恶意用户（或通过脚本）直接调用 API 构造循环 BOM，在执行 MRP 需求计算时，会导致服务器 CPU 100% 并在数分钟内导致后端服务全局 OOM 崩溃。

---
> [!IMPORTANT]
> **审计建议**：必须立即封锁 BOM 递归循环漏洞，并打通 BOM 与 Operation 的关联键，实现“精准按需”领料。

## 四、 中小企业 (SME) 实情适配与配置审计

### 4.1 业务蓝图逻辑检查 (Blueprint Integrity)
- **发现**：BOM 结构与 M-BOM（制造清单）在蓝图中并未明确区分，缺乏针对“多版本 BOM”并发的硬性配置路由。
- **实情谬误**：SME 经常需要“现场改单”，如果在蓝图层面将 BOM 锁定为单一流程，会导致当出现“替代料/紧急工艺变更”时，系统由于缺乏“工艺灵活切换”配置而无法响应。
- **证据**：`f:\dev\riveredge\riveredge-frontend\src\pages\system\business-config\BusinessFlowConfig.tsx:38`

### 4.2 参数设置有效性对账 (Parameter Effectiveness)
- **发现**：`bom_multi_version_allowed` 参数虽然存在，但实际 Designer 逻辑中缺乏基于此参数的“强制审批流”触发。
- **配置建议**：增加 `bom.allow_ad_hoc_substitute` (允许现场领料时临时替代) 参数。SME 经常出现“主料断档，拿同规格代料先用”的情况，系统应在配置项中提供此“合规后补”逻辑。

### 4.3 模具与工装 (Tooling/Mold) 的全寿命管理断层 (Tooling Lifecycle Gap)
- **发现**：系统虽有 `MoldList`，但缺乏将模具的“状态（维保中/报废）”与“工单投产”进行强校验的逻辑。
- **技术证据**：见 `work-orders/index.tsx` 第 134 行：仅能获取列表，但在 `handleSubmit` 校验逻辑中无针对模具可用性的资源冲突检查。
- **业务影响**：**生产事故风险**。工单下达到产线后才发现配套模具正在维保或已达到使用次数上限（需退火/维修），导致产线空转，严重影响交付节奏。

## 五、 改进与整改计划 (Step 5: Improvement Plan)

### 5.1 短期整改 (Immediate Actions - 1个月内)
- **[针对 3.1, 5.9]**: **递归逻辑硬化**。在后端 `bomApi.save` 接口中引入 `CycleDetector` 深度扫描。一旦发现 A->B->A 的循环依赖，立即拒绝保存并抛出物理层级的“死循环预警”。
- **[针对 4.3]**: **资源可用性门槛**。在工单创建与下达逻辑中增加 `ToolingCheck`。系统需实时对比配套模具的 `status`。若模具处于“维保/待修/报废”，系统应禁止工单下达并红色提示机台冲突。
- **[针对 5.5, 8.2]**: **替代料基础架构**。在 BOM 设计器中新增 `SubstituteGroup` (替代料组) 维护入口，允许 PMC 在领料异常时，从预设的“白名单”替代料中快速切换，而非暴力修改主 BOM。

### 5.2 中期优化 (Medium-term - 3个月内)
- **[针对 5.2, 1.9]**: **精益物料拉动 (M-BOM)**。打通 BOM 与工艺路线的 Operation 关联。实现按工序节点发料，将“工单开工一次性配料”优化为“按工序进度分批拉动”，极大降低线边仓积压空间。
- **[针对 5.3, 5.7]**: **变更影响闭环 (ECN Analysis)**。开发工程变更看板。当发布新版本 BOM 时，自动扫描所有“执行中”和“已下达”工单，提供“一键替换/损耗分析”工具，引导现场执行版本有序迭代。
- **[针对 5.4, 4.5]**: **MRP 损耗因子激活**。在 MRP 运算引擎中引用 BOM 明细的 `waste_rate`（工艺损耗率），将建议采购量由“理论净需”自动调整为“生产毛需”，消除常态化缺料。

### 5.3 长期演进 (Long-term Strategy)
- **[针对 5.8]**: **智能替代方案推荐**。集成库存实时快照，当主物料分拣失败时，由系统根据“优先级+库存结余”自动向计划员推荐最优替代料方案，实现计划层面的自愈。
- **[针对 5.6]**: **技术资产物理隔离**。重构主数据存储架构，从数据库查询层强制注入 `tenant_id` 过滤条件，确保各租户间的 BOM 技术机密在物理层面无法交叉探测。
