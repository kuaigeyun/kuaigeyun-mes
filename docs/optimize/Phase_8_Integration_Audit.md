# Phase 8: 跨模块业务集成审计报告 (Role-Driven 3-Step Audit)

**审计结论**：系统模块间对接目前处于“快照式推送”状态，缺乏“双向联动”与“实时校验”。跨模块逻辑断层导致了数据不一致、财务对账难以及生产追溯断链等核心硬伤。

---

## 第一步：角色视角补齐 (Step 1: Roles & Scenarios)
本阶段审计从以下视角穿透：
- **系统集成管理员 (Integration Admin)**: 关注数据流动的原子性、异常回调。
- **跨部门协同岗 (Cross-Dept Coordinator)**: 关注 SO-WO 联动、QC-PO 联动。

---

## 第二步：字段缺失与基础业务点审计 (Step 2: Fields & Basic Points)

### 8.1 跨模块状态变更回调字段缺失 (Missing Callback Field)
- **问题描述**：下游单据（如工单）状态变更后，无自动回调上游（销售订单）并更新可视化进度的字段设计。
- **技术证据**：见 `services/common.ts` (Event Definition)：缺失针对 `onStatusChange` 的广播属性映射。
- **业务影响**：销售人员无法实时掌握订单生产进展，必须手动打电话沟通，管理透明度极低。

### 8.2 集成日志 (Integration Log) ID 追踪缺失 (Audit Field Gap)
- **问题描述**：在从 SO 转换到 WO、PR 转换到 PO 的过程中，单据头未冗余保存源单的 UUID 快照。
- **技术证据**：见 `sales-order.ts` L1098：转换后仅记录了源单 ID，未对转换时的快照数据加签。
- **业务影响**：当源单后续被修改时，无法对比出下推瞬间的原始数据，审计链存在断裂点。

## 第三步：重大逻辑谬误审计 (Step 3: Major Logical Fallacies)

### 1.1 销售 → 生产：变更穿透力为零 (Change Impact Broken)
- **问题描述**：SO 在下推工单后修改数量，系统仅做提示，不具备对已开工工单的“强行中断”或“联调评估”逻辑。
- **技术证据**：见 `sales-management/sales-orders/index.tsx:L1098`：撤回逻辑仅基于单据存在，而非工序状态。
- **业务影响**：导致生产现场仍按旧计划加工，产生严重的呆滞料（Obsolete Inventory）积压。

### 1.2 生产 → 仓储：倒冲异常导致“库存幻觉” (Backflush Logic Broken)
- **问题描述**：报工触发的倒冲失败（缺料）时，系统仅记录失败并允许产成品入库。
- **技术证据**：见 `warehouse-management/backflush-records/index.tsx:L139`：核心流程被处理为“事后重试”而非“事中拦截”。
- **业务影响**：**库存虚增**。账面显示成品已入库，但原料却未核扣（由于倒冲失败），导致账实完全背离。

### 1.3 质量 → 生产：报工与检验强力解耦谬误 (Enforcement Logic Broken)
- **问题描述**：报工时允许工人自行声明合格数，无需关联对应的 QC 检验单。
- **技术证据**：见 `production-execution/reporting/index.tsx:L232-241`：合格数声明与提交处于同一原子操作，无外部 QC 钩稽。
- **业务影响**：大量不合格品在未经 QA 评审的情况下直接流转至下一道工序，造成质量风险失控。

### 1.4 工程 → 全局：ECN 变更的“版本黑洞” (Version Control Broken)
- **问题描述**：新版 BOM 发布后，旧版工单与备料单无自动停机或版本一致性校验。
- **技术证据**：见 `production-execution/reporting/index.tsx` (全文件)：缺乏对工单 BOM 版本相对于 Master BOM 最新性的校验。
- **业务影响**：车间可能持续生产已被淘汰的产品设计，造成巨大的呆滞物料浪费。

### 1.5 集成事务跨模块“非原子性”断裂 (Transaction Atomic Broken)
- **问题描述**：跨模块推送（如下推收货通知）时，由于缺乏分布式补偿机制，可能出现一侧成功一侧失败的中间态。
- **技术证据**：见 `demand-computation/index.tsx`：下推多张单据时未封装在统一事务内。
- **业务影响**：导致数据“悬空”。比如计算结果显示已下推，但实际采购单未生成，造成计划员的判断失误。

### 8.6 全局“业务锁” (Global State Lock) 机制缺失 (Logical Fallacy)
- **问题描述**：当上游关键单据（如 ECN 变更、信用额度调整）处于“审核中/挂起”状态时，下游关联单据（PO/WO）无法自动进入“冻结”状态。
- **技术证据**：见 `services/common.ts`：缺乏全局 `resource_locked_by` 的锁竞争与状态传播机制。
- **业务影响**：**管理失控风险**。即使 PE 已经发起了 BOM 变更申请，计划员仍能基于旧 BOM 成功创建工单并领料，导致变更指令在执行层被彻底无视。

### 8.7 跨模块事件通知的“循环触发”隐患 (Architecture Fragility)
- **问题描述**：系统缺乏对 EventBus 触发链的深度限制，存在 A 模块更新触发 B，B 更新反向触发 A 的潜在线上环路。
- **技术证据**：见 `services/common.ts`：`EventBus` 的订阅分发逻辑中未见 `trace_id` 或 `max_depth` 限制。
- **业务影响**：**系统雪崩风险**。在复杂的物料下推结算场景下，一个细微的金额微调可能引发无限次的状态同步冲突，导致数据库连接池瞬间溢出。

---
> [!IMPORTANT]
> **集成建议**：必须建立全局的 `EventBus`，强制实现在重要单据（SO/BOM）变更时下游关联单据的“自销毁”或“自锁定”逻辑，确保存量数据的实时一致性。

## 四、 中小企业 (SME) 实情适配与配置审计

### 4.1 核心配置逻辑风险 (Integration Logic)
- **发现**：`BusinessFlowConfig.tsx` 中的 `applyComplexityPreset` (L189) 的 `Simple` 模式在集成层缺乏“实质性减载”。
- **实情谬误**：中小租户在开启“极简模式”后，系统的后台 Job（如 MRP）仍按“全量计算”逻辑运行，对于 SME 这种只有几百条数据的租户来说，由于缺乏“租户规模感知”的计算路径优化，不仅浪费服务器资源，还由于不必要的校验导致操作繁琐。
- **证据**：`f:\dev\riveredge\riveredge-frontend\src\services\businessConfig.ts:189`

### 4.2 事件反馈机制缺失 (Event Feedback)
- **发现**：蓝图调整后系统缺乏“全量配置有效性自检”。
- **实情谬误**：SME 经常在生产过程中突然调整流程（例如从“先检后入”改为“由于急用先行入库”），系统集成层无法在蓝图修改瞬间反馈对“在途单据”的追溯性影响，导致流程切换后的订单处于“逻辑僵尸态”。

## 五、 改进与整改计划 (Step 5: Improvement Plan)

### 5.1 短期整改 (Immediate Actions - 1个月内)
- **[针对 8.1, 8.2]**: **联动链路补齐**。在 `services/common.ts` 中新增 `onStatusChange` 全局钩子。当工单完工时，自动反向触发销售订单的 `production_progress` 更新；同时在所有下推接口中注入 `source_uuid` 追踪 ID。
- **[针对 1.1, 8.6]**: **单据锁定机制**。实现“变更冻结逻辑”。当销售订单发起修改申请时，系统自动通过 `EventBus` 广播并暂时锁定（Read-only）下游已关联的工单与发料单，严禁在变更评估完成前继续作业。
- **[针对 1.3]**: **质检硬关联**。重构报工接口逻辑。合格数录入必须关联对应的 `inspection_id`，若质检判定结果为“不合格”，系统强制拦截报工提交。

### 5.2 中期优化 (Medium-term - 3个月内)
- **[针对 1.5, 8.7]**: **事务一致性加固**。引入“集成事务管理器”。在执行多单据并发推送（如需求计算下推）时，采用 `Two-Phase Commit` 思想并在失败时执行“状态回滚 (Rollback)”，确保数据不悬空。
- **[针对 1.2]**: **倒冲异常拦截**。修改仓库倒冲逻辑。当原材料余额不足导致倒冲失败时，系统应自动阻塞产成品入库确认，并向 PMC 推送“料差异常提醒”，强制要求先合规领料再入库。
- **[针对 4.1]**: **SME 性能分流**。针对极简模式租户，开发“轻量化 Job 路径”。将 MRP 计算等重资源消耗任务切换为“直读式计算”，绕过复杂的集团级版本校验，提升 SME 响应速度。

### 5.3 长期演进 (Long-term Strategy)
- **[针对 1.4, 8.6]**: **全局版本感知网络**。构建以物料版本为主轴的全局联动模型。当 BOM 发生 ECN 变更时，系统自动识别并精准标记所有受影响在途单据的版本偏离度，实现全自动的工程迭代管理。
- **[针对 8.7]**: **自愈式消息总线**。升级 `EventBus` 架构，引入 `max_depth` 与 `trace_id` 环路检测机制，防止大规模业务联动场景下的逻辑死循环与系统雪崩。
