# Phase 1: 销售管理与协同逻辑审计报告 (Role-Driven 3-Step Audit)

**审计结论**：销售模块在 UI 层面虽已初步补强，但底层逻辑仍处于“弱校验、快照式”状态。关键的财务精度、单据连线余量以及跨模块币种链路存在系统性断裂风险。

---

## 第一步：角色视角补齐 (Step 1: Roles & Scenarios)
本阶段审计从以下视角穿透：
- **销售人员 (Salesperson)**: 关注单价对齐、交期承诺、信用风险。
- **客户 (Customer)**: 关注发货通知准确性、报价一致性、外币结算。
- **财务人员 (Finance)**: 关注价税合规、币种一致性、尾差平摊。

---

## 第二步：字段缺失与基础业务点审计 (Step 2: Fields & Basic Points)

### 1.1 单位换算因子全局挂载 (Missing Factor)
- **问题描述**：当前销售订单总额计算逻辑（数量 \* 单价）完全忽略了物料的多单位换算比例。
- **技术证据**：见 `SalesOrder/index.tsx` 第 749-750 行。代码执行标量乘法；`src/components/material-unit-select/index.tsx` 仅返回字符串，不返回换算比例（分子/分母）。
- **业务影响**：库存扣减错误，账务金额出现百倍/千倍误差（如：按“吨”卖，但系统按“Kg”计价且库存只扣 1 个基础单位）。

### 1.2 跨模块币种链路补齐 (Missing Currency)
- **问题描述**：报价单（Quotation）有币种，但销售订单（SalesOrder）完全缺失币种存储与展示。
- **技术证据**：对比 `services/quotation.ts` 第 57 行与 `services/sales-order.ts` 第 17 行（接口定义完全缺失该字段）。
- **业务影响**：外贸业务下推时币种信息强制丢失并变为人民币（CNY），造成财务对账彻底失败。

### 2.2 销售退货：明细行缺失批次号录入 (Missing Batch Field)
- **问题描述**：销售退货录入界面不提供批次号录入，导致质量溯源链路断裂。
- **技术证据**：见 `sales-returns/index.tsx` 第 618-675 行。其表单列表缺乏 `batch_number` 输入项。
- **业务影响**：仓库入库时无法将退货归入正确的物理批次，售后追溯逻辑失效。

### 3.1 报价转订单：不支持部分行采纳转换 (Basic Flow Gap)
- **问题描述**：报价单转订单为 1:1 整体下推，不支持勾选部分明细入单。
- **技术证据**：见 `services/quotation.ts` 第 130 行 (`convertQuotationToOrder`) 及前端对应按钮。仅支持针对单一 ID 的全量转换，无子项级分片参数。
- **业务影响**：当报价 10 项客户只签 3 项时，销售员必须手动重录，极大增加差错率。

### 3.2 销售预测：矩阵录入视图缺失 (UI Pattern Gap)
- **问题描述**：缺乏基于时间轴（横向周/月）的产销预测录入矩阵。
- **技术证据**：见 `sales-forecasts/index.tsx` 第 1150-1200 行。界面为标准纵向列表，无 Grid 扩展视图。
- **业务影响**：高频预测录入效率极低，数据容易产生“计划失真”。

### 3.3 折扣金额 (Discount) 强制清零覆盖 (Basic Logic Gap)
- **问题描述**：即使界面提供了折扣字段，在提交保存时代码会无差别重置为零。
- **技术证据**：见 `sales-orders/index.tsx` 第 733 行：`values.discount_amount = 0;`。
- **业务影响**：业务员无法记录任何非标促销或商务折让，导致最终应收款与合同额永久性无法对平。

## 第三步：重大逻辑谬误审计 (Step 3: Major Logical Fallacies)

### 1.3 含税切换逻辑缺陷 (Calculation Logic Broken)
- **问题描述**：切换“价税合计”开关时，系统仅改变字段性质，未对已录入的单价进行数值转化。
- **技术证据**：见 `SalesOrder/index.tsx` 第 2335-2347 行 (`price_type` 切换开关)。该开关缺乏 `onChange` 批量转化逻辑。
- **业务影响**：当用户从“不含税 100 元”切换到“含税”模式时，金额会瞬间从 113 元（含税价）暴降至 100 元，导致严重报价错误。

### 1.4 整单金额覆盖与平摊 (Accounting Logic Broken)
- **问题描述**：汇总区域为只读显示，不支持“整单含税总金额”的录入及尾差自动平摊。
- **技术证据**：见 `SalesOrder/index.tsx` 第 169-250 行。汇总字段全为 `div` 渲染，无 `Input` 控件。
- **业务影响**：无法处理制造业合同中常见的 1 分钱税额误差，导致开票对账不平。

### 2.1 发货通知：数量下推逻辑错误 (Flow Integrity Broken)
- **问题描述**：下推发货通知单时，系统默认带入订单原始总量，而非欠发量。
- **技术证据**：见 `shipment-notices/index.tsx` 第 331-342 行。`notice_quantity` 明确取值为 `required_quantity`（总量）。
- **业务影响**：造成严重的超发风险和重复发货隐患，仓库无法基于真实余额作业。

### 2.3 库存 ATP 预占量感知缺失 (Inventory Integrity Broken)
- **问题描述**：下单时由于无法感知已预占但未发货的库存，导致虚假的可销售预判。
- **技术证据**：`sales-orders/index.tsx:25` 的 `MaterialInventoryIndicator` 仅拉取物理实有数，无分库/分状态预占接口引用。
- **业务影响**：销售员在下单时看到是绿灯（有货），实则已被占，造成交期违约。

### 2.4 用户信用额度提交硬拦截 (Risk Control Broken)
- **问题描述**：信用额度目前仅为静态展示，在订单提交时无任何代码级拦截逻辑。
- **技术证据**：见 `SalesOrder/index.tsx` 第 710-851 行 (`handleSaveInternal`)。全过程无任何查询或对比客户信用余额的 API 调用及错误提示。
- **业务影响**：超额订单可通行无阻至生产环节，造成严重的资金回笼风险。

### 2.5 数量/单价负数录入 bypass (Safety Validation Broken)
- **问题描述**：明细行录入未对负数进行拦截限制。
- **技术证据**：`sales-orders/index.tsx:124, 727, 765` 仅执行 `Number()` 转化或 `|| 0` 兜底，缺乏 `> 0` 约束。
- **业务影响**：允许录入负数数量或负单价，可能被用于非法冲账或恶意调减已入账资产。

### 2.6 浮点数运算导致的“结算粉尘”误差 (Precision Broken)
- **问题描述**：直接使用 JS 浮点算术进行价税反算，未进行分位舍入处理。
- **技术证据**：见 `sales-orders/index.tsx:129`：`const exclAmt = (qty * price) / (1 + taxRate / 100);`。
- **业务影响**：大批量交易场景下，累计尾差将导致财务科目永远无法自动出清对平。

### 2.7 状态映射 (Status) 字符串硬编码 (Architecture Fragility)
- **问题描述**：审批与下推逻辑高度依赖中文字符串枚举。
- **技术证据**：见 `sales-orders/index.tsx:67`：`const APPROVED_STATUS_VALUES = ['已审核', '审核通过', ...]`。
- **业务影响**：系统极其脆弱。任何后端多语言微调或重构均会导致前端业务按钮大面积失效。

### 1.5 价格审批流 (Price Approval) 真空 (Major Business Gap)
- **问题描述**：销售报价/订单的单价是由业务员手动输入的，系统虽有“默认售价”，但无“价格偏差审批”逻辑。
- **技术证据**：见 `sales-orders/index.tsx` 第 1318 行：`unit_price` 仅从 `defaultSalePrice` 获取初始值，但输入框无 `max/min` 的硬性审批触发逻辑。
- **业务影响**：**利润流失风险**。业务员可随意给客户极低价格（甚至 0 元）而绕过管理层审核，导致企业核心利润空间失控。

### 1.6 ATP (Available to Promise) 静态化谬误 (Logical Fallacy)
- **问题描述**：交期预测仅基于“当前库存”，未集成“未来产出”（工单预计完工）与“未来入库”（采购预计到货）的时间轴。
- **技术证据**：见 `sales-orders/index.tsx` 第 1371 行：`delivery_progress` 仅为进度展示，无后端 ATP 动态承诺引擎支持。
- **业务影响**：**交付信誉风险**。销售承诺的交期完全凭经验，无法在下单瞬间根据生产排程给出“可承诺日期”，导致订单大量逾期或频繁改期。

### 1.7 MTO 与 MTS 衔接的“二元逻辑”断裂 (Integration Gap)
- **问题描述**：系统将“按单生产 (MTO)”与“按库生产 (MTS)”处理为手动的“下推”操作，缺乏基于物料属性的自动路由。
- **技术证据**：见 `sales-orders/index.tsx` 第 1042 行：`handlePushToWorkOrder` 是一个纯手动 UI 动作，不判断物料是否已有常备库存。
- **业务影响**：**库存积压与重复生产**。即使仓库有现成成品，销售仍可能由于“手动下推”惯性触发新的生产工单，造成资源极大浪费。

### 1.8 销售价格与物料成本的联动校验真空 (Margin Oversight Gap)
- **问题描述**：下单时系统不显示物料的“参考成本”或“最近采购价”，且无销售毛利预警逻辑。
- **技术证据**：全量检索 `sales-orders/index.tsx` 结果显示搜索 `cost` 匹配项为 0。
- **业务影响**：**利润流失风险**。在中小型企业价格波动大的环境下，业务员可能以低于成本的价格成交而不自知，导致越卖越赔。

---
> [!IMPORTANT]
> **审计结论**：必须立即封锁负数操作口，强化币种/换算因子的全链条穿透，并将信用风控从“展示级”升级为“阻断级”。

## 四、 中小企业 (SME) 实情适配与配置审计

### 4.1 业务蓝图逻辑检查 (Blueprint Integrity)
- **发现**：`BusinessFlowConfig.tsx:243` 等处硬编码了“销售蓝图”及其节点路由。
- **实情谬误**：中小企业销售流程极不固定，经常出现“先提货后补单”或“无预测紧急单”。当前蓝图中，将 `sales_forecast` 设为 `medium/large` 的必选或勾选项，但在实务中，90% 的 SME 并不使用预测，导致蓝图配置与实务产生“逻辑冗余”。
- **证据**：见 `f:\dev\riveredge\riveredge-frontend\src\pages\system\business-config\BusinessFlowConfig.tsx` 第 243 行。

### 4.2 参数设置有效性对账 (Parameter Effectiveness)
- **发现**：虽然配置页有 `sales.audit_enabled` 开关，但其他细粒度控制处于真空。
- **缺失证据**：`parameters.sales.allow_over_delivery` (超交控制) 仅在 UI 存在，代码未引用。
- **配置建议**：针对 SME 频繁的“紧急提货”，应增加 `sales.emergency_bypass_token` 参数，允许在订单未审核时先行触发仓库任务，并在 24 小时内强制回补单据。

## 五、 改进与整改计划 (Step 5: Improvement Plan)

### 5.1 短期整改 (Immediate Actions - 1个月内)
- **[针对 1.1, 2.6, 8.1]**: **计算精度加固**。引入 `decimal.js` 统一处理 `sales-orders` 的价税反算与单位换算，在提交前注入物料主数据的 `conversion_factor` 换算比例。
- **[针对 2.5, 7.6]**: **合法性硬拦截**。在 `handleSave` 逻辑中增加 `qty > 0` 与 `price >= 0` 的强制校验，并封锁 API 层面的负数注入。
- **[针对 3.3]**: **逻辑纠偏**。移除 `sales-orders/index.tsx:733` 的 `discount_amount = 0` 硬编码，恢复折扣业务字段的真实性。
- **[针对 2.7]**: **架构解耦**。将单据状态从“中文字符串”枚举重构为 `enum` 编码，确保多语言与后端重构时的系统稳定性。

### 5.2 中期优化 (Medium-term - 3个月内)
- **[针对 2.4, 9.7]**: **信用风险阻断**。开发后端 `CreditGuard` 中间件。销售订单“确认”时需实时对比客户信用余额，超额则强制转入“高层信用审批”流。
- **[针对 1.5, 1.8]**: **利润防护墙**。实时拉取物料“参考成本”，当销售单价低于成本或毛利低于预设阈值时，系统应自动挂起单据并要求主管特批。
- **[针对 2.1]**: **下推逻辑修正**。重构发货通知单下推算法，取 `balance_quantity` (总量 - 已发量)，并在此环节实现“发货通知 -> 库存锁定”的原子事务。

### 5.3 长期演进 (Long-term Strategy)
- **[针对 1.6, 1.7]**: **动态承诺引擎 (ATP)**。集成生产排程 (APS) 与采购在途数据，实现订单交期从“凭经验”到“凭算力”的自动承诺转化。
- **[针对 1.2]**: **全链路多币种穿透**。完成从报价 -> 订单 -> 应收 -> 结账的全流程汇率快照与多币种核算逻辑，支持外币业务的真实核对。
