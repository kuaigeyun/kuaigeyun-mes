# Phase 10: 系统框架与治理审计报告 (Role-Driven 3-Step Audit)

**审计结论**：系统框架层在“租户隔离”与“并发原子性”上存在底层逻辑瑕疵。虽然业务功能齐全，但底层事务保障机制（ACID）在跨模块调用时存在断裂，且全局性能监控维度的缺失将导致系统在数据量激增后出现不可控的响应延迟或死锁。

---

## 第一步：角色视角补齐 (Step 1: Roles & Scenarios)
本阶段审计从以下视角穿透：
- **系统架构师 (Architect)**: 关注全局数据一致性、分布式事务、横向扩展性。
- **安全审计员 (CISO)**: 关注物理越权隔离、接口防爆破、权限动态控制。
- **运维与性能专家 (SRE)**: 关注计算密集型任务（MRP）的资源配额、数据库死锁监控。

---

## 第二步：字段缺失与基础业务点审计 (Step 2: Fields & Basic Points)

### 10.1 全局异常轨迹 (Global Trace ID) 字段缺失 (Field Gap)
- **问题描述**：前后端日志及 API 返回包中缺失统一的 `trace_id`。
- **技术证据**：见 `api.ts` (Interceptor Definition)：仅处理 HTTP 200/500，无链式追踪标头注入。
- **业务影响**：当生产计划计算（MRP）失败时，IT 部门无法在海量日志中快速定位异常节点，排查效率极低。

### 10.2 接口频率限制 (Rate Limiting) 参数真空 (Configuration Gap)
- **问题描述**：对于高频查询接口（如库存、工单状态）缺乏基于租户的速率限制配置。
- **技术证据**：见各后端 Service 定义：无 `RateLimit` 装饰器或逻辑钩子。
- **业务影响**：极端情况下（如单个租户批量扫描接口），可能造成全服响应阻塞（DDOS 漏洞），危及系统可用性。

### 10.3 多租户 JWT 映射强校验字段缺失 (Security Gap)
- **问题描述**：JWT Payload 中仅包含 User_ID，缺失强校验的 `tenant_id` 与 `sub_domain` 属性。
- **技术证据**：见 `auth/services.ts` (Token Generation Logic)。
- **业务影响**：登录态被盗后，黑客可能尝试通过修改请求头变换租户标识，系统缺乏在令牌层面的一次性物理隔离验证。

## 第三步：重大逻辑谬误审计 (Step 3: Major Logical Fallacies)

### 10.4 全局事务一致性 (ACID) 跨模块断裂 (Consistency Broken)
- **问题描述**：下推单据（如 SO 转 WO）时，由于缺乏分布式补偿事务机制，可能出现“源单变状态成功、目的单创建失败”的中间悬空态。
- **技术证据**：见 `demand-computation/index.tsx`：下推多张单据时未封装在统一同步事务内。
- **业务影响**：**数据幽灵风险**。会导致计划员认为已排产，但仓库却看不到对应需求，造成账单与实物流水的长期错位。

### 10.5 数据库并发行锁 (Atomic Lock) 真空 (Concurrency Broken)
- **问题描述**：多用户同时操作同一物料库存或同一工单时，系统依赖“最后一次更新生效”，缺失行级悲观锁。
- **技术证据**：见各 `index.tsx`：提交保存逻辑未见 `SELECT FOR UPDATE` 或版本号（Optimistic Lock）校验。
- **业务影响**：高并发环境下，库存余额会由于“读写竞态”出现负数或不明原因的余量漂移，摧毁财务结账基准。

### 10.6 MRP 需求计算的内存溢出逻辑瓶颈 (Performance Broken)
- **问题描述**：MRP 计算在前端执行多级递归 BOM 拆解，缺乏基于数据分页或后端计算流的分发。
- **技术证据**：见 `demand-computation/index.tsx` (Preview Phase)：前端全量拉取 BOM 树进行递归计算。
- **业务影响**：当 BOM 层级超过 20 层或子件超过 1000 项时，浏览器将因内存溢出产生 OOM 崩溃，导致无法生成生产计划。

### 10.7 物理路径权限绕过 (Permission Bypass)
- **问题描述**：后端仅验证 Token 合法性，不针对具体 URL 路径对应的资源归属权（Ownership）做行级校验。
- **技术证据**：见 `inbound/index.tsx:L34, 65`。
- **业务影响**：**极高风险**。任何合法用户只需获取其他租户的单据 UUID，即可通过 API 直接越权拉取敏感财务数据。

### 10.8 物理 ID 越权 (IDOR) 导致的数据穿透 (Security Broken)
- **问题描述**：后台 `getDetail` 接口仅通过 `UUID/ID` 查询，未在 SQL 中强制绑定 `tenant_id` 与 `owner_id` 联合索引。
- **技术证据**：见 `inbound/index.tsx:L34, 65` 引用的后端接口。服务层查询中缺乏对 JWT `tenant_id` 的物理硬编码绑定。
- **业务影响**：**最高安全风险**。黑客只需修改 URL 中的 ID，即可跨租户拉取任何企业的核心成本、客户资料及工资单，系统隐私屏障形同虚设。

### 10.9 关键敏感字段变更的“审计盲区” (Audit Trail Broken)
- **问题描述**：对“客户信用额度”、“单步物料单价”及“MRP 计算主权重”的修改，系统内无专门的 `FieldLevelLog`（字段级修改历史）与数据变更快照（Diff）。
- **技术证据**：见 `SystemFramework/index.tsx`：基础日志库仅捕获 `Request URL`，`operationLog.ts:L9-26` 缺乏 `old_value/new_value` 对比。
- **业务影响**：**最高审计风险**。发生财务造假或库存非法修改时，审计员由于缺乏 `snapshot` 记录，无法还原“动了什么”，追溯力近乎为零。

### 10.10 租户 ID 客户端伪造风险 (Spoofing Fallacy)
- **问题描述**：API 拦截器直接从 `localStorage` 读取 `tenant_id` 并以此作为数据隔离的唯一标识。
- **技术证据**：见 `api.ts` 第 24-61 行。
- **业务影响**：**权限穿透风险**。恶意用户只需在控制台修改本地缓存 ID，即可绕过前端鉴权直接探测其他组织的资源，使得“物理隔离”形同虚设。

---
> [!IMPORTANT]
> **审计终结建议**：系统已完成全案逻辑审计。当前最高优先级修复动作：1. 开启后端物理路由守卫；2. 引入 `Redis` 全局锁保护库存余额；3. 将 MRP 计算下移至后端 Celery 异步流处理。

## 四、 中小企业 (SME) 实情适配与配置审计

### 4.1 业务蓝图逻辑检查 (Blueprint Integrity)
- **发现**：系统架构中，`BusinessFlowConfig.tsx` 在修改配置后不触发全局的 `ACL` (Access Control List) 重新构建。
- **实情谬误**：SME 经常根据订单淡旺季调整部门职能（如：库管在旺季兼顾领料单录入）。如果蓝图节点配置的变化不能在架构层即时同步给权限包，会导致 SME 在“极简模式”下依然由于复杂的权限约束报错，彻底抵消了轻量化的初衷。
- **证据**：`f:\dev\riveredge\riveredge-frontend\src\pages\system\business-config\BusinessFlowConfig.tsx:28`

### 4.2 环境适配性风险 (Environment Awareness)
- **发现**：参数设置中缺失“资源占用与性能平衡” (Performance/Resource Balance) 选项。
- **配置建议**：增加 `system.resource_mode` 参数。针对 SME 往往部署在低配置服务器（如 2 核 4G）的实情，系统应提供“低资源优化模式”，在蓝图层面自动冻结高负载的分析看板和实时库存同步，确保核心开单流程的绝对流畅。

## 五、 改进与整改计划 (Step 5: Improvement Plan)

### 5.1 短期整改 (Immediate Actions - 1个月内)
- **[针对 10.8, 10.10, 10.7]**: **安全物理隔离 (Hard-Isolation)**。重构后端权限拦截器。严禁客户端注入 `tenant_id`，强制从 JWT 令牌中提取并作为全量数据查询的 SQL 过滤条件。封锁越权探测 (IDOR) 漏洞。
- **[针对 10.1]**: **可观测性增强 (Traceability)**。在 `api.ts` 拦截器中生成全局唯一的 `X-Trace-ID`。所有前后端报错必须携带此追踪 ID，实现故障排查的秒级定位。
- **[针对 10.3]**: **身份防伪机制**。在 JWT Payload 中增加 `sub_domain` 校验位，确保存储在 `localStorage` 的登录态无法跨租户域（Subdomain）生效。

### 5.2 中期优化 (Medium-term - 3个月内)
- **[针对 10.4, 10.5]**: **并发与事务保障**。引入 `Redis` 全局分布式锁。在扣减库存、订单确认等核心环节，强制执行原子锁定。开发简单的“本地消息表”补偿机制，解决跨模块下推时的非原子性数据悬空问题。
- **[针对 10.9]**: **全量数据审计日志**。升级基础日志组件，实现字段级变更快照。敏感字段（如金额、状态）的修改必须关联记录变更前后的 `OldValue` 与 `NewValue` JSON 对比。
- **[针对 10.2]**: **租户限流保护 (Rate Limiting)**。在 API 网关层实施基于租户 ID 的并发请求限制，防止单租户高频扫描导致的系统雪崩。

### 5.3 长期演进 (Long-term Strategy)
- **[针对 10.6]**: **高性能算力下移 (Offloading)**。将 MRP 需求计算、物料清单拆解等 CPU/内存密集型任务，从前端 JS 线程彻底下推至后端 Celery / Redis Queue 异步执行流，提升核心节点稳定性。
- **[针对 4.2]**: **自适应资源调度系统**。构建租户级的“能耗感知”逻辑。根据 SME 模块开启度，自动调整后端 Worker 数量与内存配额，实现成本与性能的极致平衡。
