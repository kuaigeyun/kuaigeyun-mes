# 高级指标卡与微缩图表（Sparkline）设计与开发规范

在重构核心系统页面（操作日志、登录日志、在线用户、数据备份）的顶部指标卡（KPI Cards）的过程中，我们打磨出了一套兼顾视觉美学、响应式布局以及数据准确性的最佳实践。

为了方便后续在整个 SaaS 平台中推广复用，特提炼总结本规范。您可以将其作为团队前端和后端的标准开发沉淀，以确保全站指标卡体验的一致性、美观性和数据处理的准确性。

## 1. 响应式布局规范 (Layout & Responsiveness)

- **动态等比分配**：抛弃过去写死的 `xs={24} sm={12} span={6}` 这种强断点控制策略。
- **Flex 弹性折行**：使用 Ant Design 的 `<Row wrap={true}>` 作为容器，内部的 `<Col>` 统一设置 `style={{ flex: '1 1 240px', minWidth: 240 }}`。
- **最终效果**：无论页面配置了 3 个、4 个还是 5 个卡片，它们都会**自动等宽平摊满整行**。当屏幕缩窄到单个卡片不足 `240px` 时，它会丝滑地自动折行，且折行后的大卡片依然会充满下方可用宽度，绝不留白。

## 2. 趋势折线的适用场景 (When to use Sparklines)

设计规范不应强制所有卡片使用折线。必须根据数据的业务属性进行取舍：

- **累积/趋势类数据**（如：总登录次数、已处理订单）：**建议使用**背景平滑曲线（Sparkline）。这能让用户一眼感知到当日流量的爆发力，增加页面的“呼吸感”。
- **即时/状态类数据**（如：实时在线人数、CPU 占用、库存余量）：**不建议使用**平滑背景折线。状态类数据由于波动可能无规律，强行平滑会导致误判，保持纯净背景更能突出当前的即时数值。

## 3. 微缩图表视觉美学 (Aesthetics & Sparklines)

若要给重点指标加入“悬浮呼吸感”的底部背景趋势图（Sparkline），需严格遵循以下层叠与样式调优：

- **卡片遮罩 (Card)**：
  - 卡片外层必须设置：`position: 'relative', overflow: 'hidden'`。
  - 卡片内容区 (`styles.body` 或直接作用于 bodyStyle)：`position: 'relative', zIndex: 1`（确保被提升的数字和文字始终覆盖在底层图表之上）。
- **底层包裹 (Chart Wrapper)**：
  - 使用绝对定位，并**稍微向下溢出边框来隐藏难看的底部闭合线**：
    ```css
    position: 'absolute',
    bottom: -18px,
    left: -16px,
    right: -16px,
    height: 76px,
    zIndex: 0,
    pointerEvents: 'none'
    ```
- **面积图配置 (@ant-design/charts Area)**：
  - **曲线形态**：绝对不要用生硬的折线，必须配置 `shapeField="smooth"`（平滑贝塞尔曲线）。
  - **渐变融合**：放弃生硬的纯色，使用垂直透明渐变：`fill: 'linear-gradient(-90deg, transparent 0%, ${特征色} 100%)'`。
  - **不透明度与描边**：配合渐变，设置底色 `fillOpacity: 0.2`；并增加鲜明的顶部主线条 `stroke: '${特征色}', lineWidth: 2`。

## 3. 指标内容排版规范 (Content & Metrics)

- **避免长文本容器撑破**：无论卡片拉多宽，都**不要在卡片内展示极长且不换行的字符串**（例如未经处理的模块长路径名 `apps/kuai-zhizao/...`）。如有枚举类统计，若单项名称过长，应当使用 `Tooltip` 或省略号 CSS (`text-overflow: ellipsis`) 截断，否则被撑破的元素会破坏父级的 Flex 布局体系。
- **排序权重与动线**：带有**趋势折线图的主级指标**（例如总访问量、当前活跃度、今日新增等“律动”数据）应放置在**第一个或者第二个**（用户视觉最易聚焦的左列侧）。静态的枚举分布类的标签（Tags）排在后边。
- **同环比组件 (DoD / YoY)**：在 `description` 位置增加诸如“较昨日”的辅助信息时，建议封装统一的 `renderDOD(today, yesterday)` 渲染函数逻辑：
  - 数值正负对应箭头（`↑ / ↓`）。
  - 绑定明确且统一的状态色（通常正数为警戒红 `#cf1322` 或增长绿 `#52c41a` 视业务而定；如果是错误日志，增长显然要标记为红色，反之下降要标记为绿色 `#3f8600`）。

## 4. 后端时区计算防坑铁律 (Backend Timezone Safe-Guard)

在处理“今天”、“昨天”、“最近 7 天”的业务趋势统计等与“当天 0 点”严格挂钩的数据时：

- **严禁使用 `date.today()` 拼凑原生的日期界限验证。**
- **统一使用 `Asia/Shanghai` 视界**：必须考虑到部署服务器可能在任何时区（或者是隔离的纯 UTC Docker 容器）。在代码侧，需通过 `zoneinfo.ZoneInfo("Asia/Shanghai")` 计算出使用者处于当地东八区下严格的 `00:00:00` 到 `23:59:59`界限。（如果在全局通用平台，应读取租户的时区配置）。
- **向 UTC 投影查询数据库**：将已获取的具备感知的（Timezone-Aware）本地时间起止点，通过类似系统底层提供的 `to_naive_utc()` 工具彻底转换为无时区的 Naive UTC 数据，最后再送入 ORM 的 `created_at__gte` 条件中执行比对。

**为何这么做？**
直接比较本地 `date` 或是强转可能导致**“早上 8 点前的统计数据总是丢失或推迟被算作了昨天”**的著名的“八小时偏移 Bug”。所有存入数据库里的底层时间戳都是基于格林威治标准时间戳（UTC）保存，统计时先还原“本地零点对应的绝对 UTC 时间界限节点”再去拦截，才是绝对安全的手段。
